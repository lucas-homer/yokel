# Docling round-two diagnostic collection

Twenty exact frozen input PDFs (34 pages) completed locally with zero operational failures. No reference answers or scores were consulted during parsing. This is the existing diagnostic corpus, not held-out validation and not a content-accuracy finding.

Configuration: Docling 2.134.0, standard PDF pipeline, table structure enabled, Apple Vision OCR through OcrMacOptions (accurate, en-US, adaptive rather than forced full-page OCR), Docling layout/table models on CPU with 4 threads. All Docling content layers, including furniture, are included in Markdown. No remote inference, prompts, external plugins or credential access. Initial package/model downloads used public repositories; HF implicit-token use was disabled. Pipeline defaults/options, Python/OS/hardware and limitations are retained in runtime.json. Exact resolved package versions are in requirements.lock.txt.

Official references: [installation/OCR selection](https://docling-project.github.io/docling/getting_started/installation/), [pipeline options](https://docling-project.github.io/docling/reference/pipeline_options/), [OCR example](https://docling-project.github.io/docling/_generated/examples/full_page_ocr/). Version selection preceded parsing; no backend/configuration tuning occurred after viewing outputs. A01(scanned) and A06(text PDF) were the operational pilots; acceptance required SUCCESS, expected page count and nonempty Markdown. Both succeeded, then the remaining 18 ran with the same options. Parsing was serial; a three-consecutive-failure stop was implemented and never triggered.

Each fixture directory retains full output.md, full Docling output.json, capture.json (input hash, status, page count, confidence/errors, timing/CPU/RSS and output hashes), and a byte-identical copy of the original frozen native.txt. The native copy is provenance for the earlier embedded-text baseline; it is not new Docling OCR output. input-plan.json contains only parser metadata, input/native hashes and pilot rules. It does not contain answers. model-cache-manifest.json hashes retained model/cache files; validation.json records resolved model revisions.

Validation passed for all 20 input/output/native hashes, DoclingDocument JSON schemas, exact full-layer Markdown re-export, expected 34 pages, and all 141 frozen companion file hashes. The original freeze and previous artifacts were untouched. Full output content remains unscored for independent review.

Compute: Mac16,10 arm64, 32 GiB RAM, 10 physical CPUs. One cold A01 conversion took 20,102 ms, including possible model download/lazy initialization/OCR warmup. The other 19 reused the converter: median 1,027 ms, range 351–2,391 ms. These are one-run conversion-wrapper wall times, not an isolated benchmark or a cloud latency comparison. Peak process RSS was 1,757,904,896 bytes (macOS cumulative high-water mark); Apple Vision's internal accelerator selection is not controlled by the CPU layout/table setting. Energy, full-machine memory load and opportunity cost were not measured. Initial installation and model download overhead must not be treated as zero.

Isolated runtime and downloaded weights remain under /private/tmp/docling-round2-20261006; the environment was 1.4 GiB at measurement. No system package/global trust/app configuration changes were made. Model revisions: docling-models v2.3.0 resolved fc0f2d45e2218ea24bce5045f58a389aed16dc23; docling-layout-heron main resolved 8f39ad3c0b4c58e9c2d2c84a38465abf757272d8. These exact revisions and hashes identify the used artifacts, although the layout alias was not immutable before its initial download.
