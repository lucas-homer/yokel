# Independent assessment: recurring runner authorization

The proposal is sound as a way to remove **per-experiment native-reader enrollment**. It is not yet a complete design for **unattended job release**. I agree with DECISION.md's separation of those outcomes and its hold on production trust changes. No blocking conceptual defect found, but signer custody/release authority remains an unresolved deployment decision. This assessment reviews the two supplied documents; it does not independently verify installed ACL state, signing identities, or platform behavior.

A byte-stable executor can continue using the same narrowly trusted reader while job data changes. An authenticated job still needs a signature. If the owner signs or touches a hardware key every time, the interaction has moved from macOS enrollment to job release; the repeated token-entry problem can improve without making the workflow autonomous. Fully unattended release requires a previously delegated authority able to sign without another owner action. No such protected signer is established in the proposal. Calling signed manifests an automatic solution before choosing that authority would overstate the result.

Authority must be explicit:

- A stable code-signing key can authorize replacement reader code. Within the stated trust design, that is authority over the bootstrap Keychain token and the service account, not merely this experiment.
- A manifest key authorizes the pinned payload to receive the allowed provider credentials. It is narrower if the immutable executor really keeps the service token out of the payload and fixes the reference envelope, but signed arbitrary Python can still spend with or export the provider keys it receives. A stronger-only job should receive OpenRouter alone.
- A signer callable without restriction by the same agent that edits the payload supplies integrity and provenance, not independent approval. Owner acceptance of that arrangement is a delegation of credential-bearing execution authority and must be described plainly.
- A separately protected signer can enforce delegated release rules, but exact approval/artifact evidence and its validation must be designed. Another agent's prose “approved” does not itself establish a protected release boundary.

The executor's native-enforced limits are job identity/signature, reference subset, argv grammar, file hashes, launch count and timeout. Per-provider call counts and spend remain properties of reviewed payload/ledger code. A signed budget field cannot independently limit a provider bill. The reports acknowledge this correctly. Do not enlarge this migration into a transport broker unless independent spend enforcement is an actual user requirement.

**Proportional choice:** if the immediate goal is to avoid repeated macOS re-enrollment while keeping explicit release approval, first assess the shorter stable-code-signing alternative *if a suitable protected signing identity already exists*. Its trust continuity needs a two-build synthetic test on the Mini, and its signing key grants broader authority than a manifest key. Do not inventory/access a private key or change ACLs as an implied next step. If no signing infrastructure exists, creating either code-signing or manifest-signing custody is real new work; neither is a free shortcut.

For a continuing workflow with many reviewed experiments, a stable executor with a minimal signed-job format is a defensible long-term choice. Keep the first implementation to the fixed Python/adapter grammar and current credential-reference envelope. The signing service, user-presence policy and maintenance burden should be chosen before implementing a large release system. A nonsecret prototype is useful to make the migration reviewable, but cannot validate production Keychain continuity or establish authority by itself.

The concrete owner decision is: **Who may release future reviewed jobs without another owner action, and within what provider/project/job/spending scope?** There are three honest choices: owner-mediated signing per release; a separately protected signer with bounded standing delegation; or explicit trust in the primary agent to authorize jobs within the executor envelope. The last choice may remove more friction, but relinquishes independence from that agent. The first keeps interaction. The second adds infrastructure and operating responsibility. Choosing an algorithm or a “stable” filename does not resolve this decision.

Before production migration, the reviewable package should identify the exact executor digest, trusted public-key fingerprint, signing-key custody and invocation policy, immutable reference/argv envelope, release-approval evidence, revocation/recovery procedure and one-time ACL migration. Synthetic checks should demonstrate altered/unsigned/expired/substituted jobs are denied, consumed jobs do not relaunch, and a second separately signed job runs without changing reader bytes. Verify actual no-prompt behavior after the explicit migration rather than promising it from architecture alone. Same-user rollback, filesystem races and process-memory access remain outside the claimed protection, as the proposal states.

The stronger-cap experiment is separable: its request/ledger review can finish now, while native release remains held. This assessment authorizes no implementation, signing, private-key or token access, ACL change, native build, paid call, or reuse of old frozen jobs. Only this assessment file was written.
