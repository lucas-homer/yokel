# R17 dispatch inventory: reuse of the R14 paid path

**Purpose.** Read-only map for preparing (not dispatching) the approved R17 comparison. No job, runner, release script, or provider was run for this inventory. No credential values were read or copied.

## VERIFIED — R14 path and its evidence

1. **Freeze/build the request in the adapter.** R14's `runtime/contract.py` imports the exact pinned `protocol-revised/compact.py`; `build(source)` checks reconstructed source, the R14 schema, canonical request digest, and request body. `validate_response(...)` performs the protocol validation, schema check, and compact/expanded inverse checks (`round14-semantic-contract/runtime/contract.py:1-23`). The adapter pins the source, protocol, dependencies, code, review, and authorization inputs before dispatch (`runtime/adapter.py:75-104`; `runtime/README.md:5-7,13`). Its fixed request settings were `openai/gpt-6.1-sol`, low reasoning, `max_tokens: 8192`, OpenAI-only routing, no provider fallback, and prompt/completion price limits 2/10 (`protocol-revised/request-settings.json:1-21`; `runtime/adapter.py:90-97`).

2. **Release and sign the frozen job.** The R14 receipts say the owner-delegated primary released signed native jobs, recorded manifest hashes, and received successful native `check-job` results before execution (`release-receipt.json:1-11`; `recovery/RELEASE-RECEIPT.json:1-11`). The recovery job proposal pins the exact isolated Python entry point, adapter, and dependency files and carries prior/reservation/ceiling metadata (`recovery/RELEASE-JOB-PROPOSAL.json:1-18`; `runtime/README.md:13`). The pre-dispatch replacement changed only job ID/expiry and attached a review; it kept the source, payload, limits, and budget unchanged (`recovery/RECOVERY-RELEASE-REVIEW.md:3-7`). ADR 0012 delegates release authority to the primary for reviewed work in the owner's scope/budget, and says signatures prove artifact integrity/identity rather than independent review (`docs/decisions/0012-stable-research-job-release.md:10-18`).

   **Important implementation distinction:** `tools/research-credentials-stable/` documents a newer *candidate*, explicitly “not installed or enrolled” (`README.md:1-8`). Its specified release process canonicalizes a `yokel.research-job.v1` manifest, signs the bytes with detached P-256 ECDSA/SHA-256, publishes manifest/signature exclusively, then calls native `check-job` (`README.md:47-60`; `release.py:12-22,56-75`). `release_job.sh` runs that release tool in a cleaned environment (`release_job.sh:1-6`). `build.py` compiles and ad-hoc signs a stable executor on the Mac Mini (`build.py:1-2,38-51`). These files explain the intended stable-manifest design; the records do **not** establish that this candidate's `release.py`/wrapper signed R14's jobs. The exact R14 signing implementation/algorithm is not identified by its receipts. Do not represent the candidate as the executed R14 signer.

3. **Run on the native host and inject credentials.** The decision and release-tool documentation place the native service-account runner/build on the Mac Mini (`0012-stable-research-job-release.md:8`; `tools/research-credentials-stable/build.py:1-2`). R14 execution receipts show native runner exit 0 and exactly one provider request (`execution/READY.json:1-5,52-60`; `recovery/PRIMARY-POSTRUN.json:1-13`). The R14 adapter accepts only the injected `OPENROUTER_API_KEY` environment variable and posts once to `https://openrouter.ai/api/v1/chat/completions` (`runtime/README.md:13`; `runtime/adapter.py:105-112,152-153`). The credential design keeps the 1Password service-account bootstrap token in Keychain; the native runner resolves the narrowly permitted provider reference and passes only provider variables into the isolated adapter environment (`0012-stable-research-job-release.md:16-18`; candidate implementation `tools/research-credentials-stable/runner.m:119-155,253-276`). No credential value is included here. R14's successful recovery did not alter token, ACL, permissions, or executable, but the original failure cause remains unresolved (`recovery/ACCESS-RECOVERY.json:2-16`; `RECOVERY.md:1-5,31`).

4. **One-shot claim, lock, and stop behavior.** R14's adapter exclusively creates/fsyncs its run directory before the transport attempt (`runtime/adapter.py:28-37,126-133`). It rejects an existing run directory, marks dispatch immediately before the single transport call, records `automatic_retry: false`, and on failure writes a stop receipt without retry (`runtime/adapter.py:126-153`). The native job claim is also exclusive and retained: the first job's claim survived its pre-adapter failure; the replacement got a fresh job ID but used the same exclusive adapter run folder, and was explicitly treated as the single authorized first provider call, not a model retry (`RECOVERY.md:3-5`; `execution/STOP.json:4-26`). Candidate stable-runner docs likewise say the native claim precedes credential lookup and cannot be replayed; that is candidate behavior, not proof of R14's candidate installation (`tools/research-credentials-stable/README.md:54-67`).

5. **Receipts and hashes.** Adapter evidence is under `round14-semantic-contract/execution/run/`: request, span table, intent, raw response, status, content, validated and expanded outputs, result, ledger, and completion receipt. `execution/READY.json` freezes hashes/sizes for these artifacts and records one provider call (`execution/READY.json:6-63`). The intent binds request/source/protocol/span-table hashes, prior, reserve, ceiling, byte guard, output cap, and no-retry (`execution/run/intent.json:1`). Completion separately pins the evidence files; ledger records one claimed attempt (`runtime/adapter.py:141-150`; `execution/run/ledger.json:1`). The native claim/registry are outside this run-folder receipt set; their exact on-disk path is not stated in the cited R14 records.

## VERIFIED — budget and ledger

- R14's cumulative conservative debit was **$1.905990718 against its $2.00 ceiling**, leaving **$0.094009282**. This is the headroom quoted by R14 recovery and R15 acceptance, not the newly user-approved R17 comparison cap (`RECOVERY.md:15-17,27`; `round15-condition-preservation/primary/acceptance.json:22-27`).
- R14's provider-reported charge was **$0.0891335**, but it was not invoice-verified. The adapter converted reported dollars to upward-rounded nanodollars and calculated a nominal usage-rate estimate (prompt tokens × 2,000 + completion tokens × 10,000 nanodollars); conservative debit was the maximum of reservation, reported cost, and that rate estimate (`recovery/PRIMARY-POSTRUN.json:13`; `runtime/adapter.py:10-26,113-125,144-150`). The $0.20 reservation therefore set the R14 debit (`execution/run/result.json:1`; `execution/run/ledger.json:1`).
- R14 recomputed its prior from immutable historical receipts through R9/R10/R12/R13, then added R14's charge (`runtime/adapter.py:38-74`; `runtime/README.md:11`). This is a **reconstructed chain of frozen per-round receipts**, not a live cross-run billing ledger. Each run has its own ledger; the stable-executor candidate explicitly says it adds no cumulative monetary journal and that its manifest budget is metadata, not bill enforcement (`runtime/adapter.py:118-125`; `tools/research-credentials-stable/README.md:69-79`).

## VERIFIED — guards R17 must preserve

Immediately before R14 transport, the adapter required a nonempty resolved key, exact `plan == build(source)`, guarded bytes ≤40,000, sufficient reservation under ceiling, and passed integrity verification. It wrote and re-read the exact request/span table, checked request SHA-256, wrote the intent receipt, then made one POST (`runtime/adapter.py:126-133`). Post-response checks required bounded raw size, HTTP 200, expected model/provider, one choice, `finish_reason == stop`, no refusal/tool call, reported cost and token usage, then schema/protocol validation and exact inverse roundtrip before completion (`runtime/adapter.py:113-117,134-146`). Failures were charged conservatively and not retried (`runtime/adapter.py:147-151`).

For R16, `protocol-w2-1/wire.py` exports `build(source, profile)`, sizing-only `measure(source, profile)`, and `validate_response(..., profile='full', *, plan)` (`wire.py:261-275,348-357`). The request has the `r16.e2` three-key user envelope `{source_text_sha256, span_table, span_table_sha256}`; `source_text` is removed only after exact table reconstruction is verified (`wire.py:321-345`; `SPEC.md:35-51,128-160`). The API schema is strict JSON Schema response format (`wire.py:321-345`). Validation requires the original plan and binds profile, response/envelope versions, table, and request hash before parsing; it returns the expanded record (`wire.py:261-293`). R17 must therefore adapt R14's current response handling (which expects compact and expanded values) to R16's direct expanded return and retain the compact form only if the comparison protocol requires it.

The R16 README explicitly requires the dispatch adapter to pass the originating plan, recompute the ≤40,000-byte guard and SHA-256 from the **actual body immediately before transport**, raise `max_tokens` above R14's 8,192, and write a rejection receipt for every `ValueError` (`round16-wire-compat/README.md:27-31`). R14's `plan == build(source)` check alone is insufficient for R16 because a mutable plan body may change after build; R16 itself says not to trust `plan['body']` as the binding (`protocol-w2-1/SPEC.md:80-82,85-101`). R16 documents `full` and `opaque` profiles; a paired comparison requires two distinct profile-bound plans and distinct receipts/one-shot job identities (`wire.py:145-149,261-275`; `README.md:27-33`).

## INFERRED — integration gaps and decisions to carry forward

- R16 is an offline candidate; no provider call established that OpenRouter accepts/enforces its deeper strict schema. The full/opaque schema is deeper than R14's, and R14 used 7,231 of 8,192 completion tokens. The higher R17 output cap is an explicit R16 integration requirement, but its exact value and whether both profiles fit a single cap remain to be frozen (`round16-wire-compat/README.md:25-33`).
- R16's `r16.e2` request-envelope version is separate from the response wire version `r16.w1`; a wrapper that assumes the R14 four-key envelope or expects `validate_response` to return `{compact, expanded}` will not fit without explicit adaptation (`protocol-w2-1/SPEC.md:35-51,128-160`; `runtime/adapter.py:139-146`).
- R16 `validate_response` binds source/profile/table/request hash against a rebuilt plan, but dispatch still must hash/guard the actual serialized request body immediately before POST. This is an independent transport-level check, not covered by validation plan binding (`protocol-w2-1/SPEC.md:80-101`).
- Two profiles mean two provider calls if compared on paired inputs. R14's adapter and release evidence authorize a single call and single run-folder claim; it cannot be widened by swapping in R16's builder. R17 needs an explicitly reviewed multi-call adapter/ledger with distinct claims, per-call reservations, stop-on-first-uncertain behavior, and cumulative accounting within the newly authorized R17 cap. No such adapter/ledger is evidenced in R14 or R16.
- The stable candidate's manifest budget is signed metadata; adapter-side checks remain the cost/call-count enforcement. Neither the candidate nor R14 supplies a persistent, tamper-resistant cumulative spend ledger spanning future R17 jobs. Keep per-call conservative debit receipts and a primary-reconciled R17 aggregate (`0012-stable-research-job-release.md:25-27`; `tools/research-credentials-stable/README.md:69-79`).
- The user-approved **$2 total R17 comparison cap** is distinct in the task context, but the repository has no cumulative ledger that automatically reconciles it against the historical R14/R15 cap. If R17's $2 is a new experiment budget, record it as a separate ledger namespace; if it is cumulative under the old cap, the available balance is only $0.094009282. The adapter/release receipt should make the selected interpretation explicit.
