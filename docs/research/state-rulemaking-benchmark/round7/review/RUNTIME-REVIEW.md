1. **P2: close the runtime gate/state consistency table.** `protocol/evaluate.py:110–117` accepts `paired_verification_completed` with a failed arm, and accepts `verification_failed` with Jev failed but stronger called. Neither can come from the serial loop, which breaks at the first failed call. It also accepts `request_size_review` with an inventory hash but no record/payload: inventory admission failure has no inventory, while verifier admission failure already has all three hashes. Require the actual permitted combinations and reject inconsistent rows. Preserve the legitimate case Jev accepted/review plus stronger failed; do not erase its earlier judgment.
2. **P2: check the status against its retained judgment.** `observed.schema.json` permits an arbitrary optional judgment object and `evaluate.py:116` checks only coverage/review reasons for acceptance. Starting from an actual simulated negative Jev result, changing only its outer `status` to `accepted_complete` passes observation validation despite its unchanged nested `common_dimensions` all failing, `judgment.status=review`, and `complete_record_shadow_accepted=false`. Dropping the accepted stronger judgment also passes. This is an internal artifact consistency defect, not a request to prove externally trusted audits. Validate the existing judgment fields for accepted/review arms and agreement with outer status, dimensions, deterministic reasons and validation result. Do not use `source_coverage_complete` as a substitute for favorable judgment; that flag correctly means the full schedule was answered, including negative results.
3. **P2: enforce the existing PDF page cap before dispatch.** `runtime/run_pipeline.py:62–66` relies only on pipeline source validation, which checks pages >=1 but no upper cap; `provider_adapters.LIMITS['PDF_pages']=40` is unused here. A valid small fixture with `pdf_pages=41` dispatches inventory, Jev and stronger and reaches paired completion. Apply the existing runtime cap at the source gate and require zero synthetic dispatch. No cohort runner or new budget framework is requested.
4. **P2: accept JSON integer values under schema type number.** `pipeline.schema_errors` classifies Python ints as integer and rejects them when the schema declares number. The new observed cost schema declares number|null, so known costs `0` and `1` fail while `0.0` passes. Preserve boolean exclusion, but treat integer as a valid JSON Schema number (or use an equivalent explicit schema union). Test through observation/evaluator with zero, positive integer, float, null and boolean; no fabricated zero for unknown cost.
